# 03 · 写作图与生成链路

> 02 篇讲的是引擎本身（怎么驱动一张图）；本篇讲的是 MoLan **实际声明的那张图**——"生成一章小说"这条链路：16 个节点、三种模式路径、两个质量门、三处回环，以及入口/出口、取消与落库。引擎负责"跑图"，本篇的这张图才是"写一章小说"的具体编排。

---

## 1. 本篇范围

这张图把一次章节生成拆成三组职责：

- **规划组**（仅 FULL 模式）：卷级编排 → 章纲 → 伏笔/角色双路规划 → 世界观校验 → 思路选择。
- **写作与质检组**（全模式）：写作 → 反 AI 味门禁 → 自审 →（按模式）一致性/深度校验 → 质量打分 → 审校路由。
- **收尾组**：事实锁校验 → 摘要 → 保存与后处理。

节点拓扑的声明全部集中在 `MultiAgentNovelService` 的构造函数里（`backend/src/main/java/com/novel/system/service/chapter/MultiAgentNovelService.java:38-80`），本文所有边、检查点、重试预算都引自这段代码。

---

## 2. 入口与模式选择

生产上只有两个入口，模式由"是否带 SseEmitter"决定：

| 入口 | 调用的方法 | 运行模式 | 触发场景 |
| --- | --- | --- | --- |
| `MultiAgentChapterGenerationService.java:67` | `writeChapter(...)` | **FULL** | 非流式（同步）整章生成 |
| `StreamingChapterController.java:156` | `writeChapterStreaming(..., sseEmitter, cancelFlag)` | **STREAMING** | 前端 SSE 流式逐 token 输出 |

模式判定是一行代码（`MultiAgentNovelService.java:157`）：

```java
Mode mode = sseEmitter != null ? Mode.STREAMING : Mode.FULL;
```

`writeChapter` 传 `null` → FULL；`writeChapterStreaming` 传 emitter → STREAMING。

**边界（如实记录）**：引擎与图定义都支持第三种模式 `Mode.FAST`（图里 `edge("outline","writing", Mode.FAST)`、`conditionalEdge("self_review","summary", mode==FAST)`、`FactLockViolationNode` 的 FAST 跳过分支都引用了它），但**当前没有任何生产入口会构造一次 FAST 运行**——上面两个入口只会产生 FULL 或 STREAMING。FAST 是"引擎可达、图已定义、但跑不到"的状态，保留它是为了未来一条最轻的生成路径。

## 4. 图拓扑与三条路径

边清单（逐条对应 `MultiAgentNovelService.java:38-80`）：

```
普通边
  arc_check        -> outline
  writing          -> deslop_check
  deslop_check     -> self_review
  fact_lock_violation -> summary
  summary          -> post_process
模式限定边
  outline      -> clue_planning          (FULL)
  outline      -> writing                (FAST)
  outline      -> writing                (STREAMING)
  world_validate -> idea_select          (FULL)
  idea_select  -> writing                (FULL)
  continuity_validation -> validation    (FULL)
  continuity_validation -> summary       (STREAMING)
  validation   -> quality_scoring        (FULL)
  quality_scoring -> audit_router        (FULL)
条件边（按声明顺序，先命中先赢）
  deslop_check  -> writing     当 deslopDecision == REWRITE
  self_review   -> writing     当 draftContent.severity == HIGH 且 writeRetryCount < 2
  self_review   -> summary     当 mode == FAST
  self_review   -> continuity_validation  当 mode == FULL 或 STREAMING
  audit_router  -> fact_lock_violation   当 auditDecision == PASS   (FULL)
  audit_router  -> outline               当 auditDecision == REPLAN (FULL)
  audit_router  -> writing               当 auditDecision == REWRITE(FULL)
  （auditDecision == MANUAL_REVIEW 不匹配任何条件边，落到 audit_router 的兜底节点
    fact_lock_violation —— 见第 5 节）
扇出/扇入
  outline --FULL--> [clue_planning ∥ character_planning] --扇入--> world_validate
检查点
  outline / writing / audit_router
重试预算（耗尽走兜底）
  outline        上限 2，兜底 -> summary
  writing        上限 3，兜底 -> fact_lock_violation
  audit_router   上限 2，兜底 -> fact_lock_violation
```

由此得到三条实际路径：

**FULL（主链路，最全）**

```
arc_check -> outline
           -> [clue_planning ∥ character_planning] (扇出) -> world_validate   (扇入)
           -> idea_select
           -> writing -> deslop_check -> self_review
                      -> continuity_validation -> validation
                      -> quality_scoring -> audit_router
                                 PASS   -> fact_lock_violation -> summary -> post_process
                                 REWRITE -> writing
                                 REPLAN  -> outline
                                 MANUAL_REVIEW -> fact_lock_violation（兜底）-> summary -> post_process
```

**STREAMING（前端流式）**

```
arc_check -> outline -> writing -> deslop_check -> self_review
         -> continuity_validation -> summary -> post_process
```

相对 FULL：跳过规划扇出（clue/character/world/idea）与深度校验段（validation/quality_scoring/audit_router），保留 `continuity_validation` 做轻量一致性检查，且 `self_review` 之后直接进 `summary`。

**FAST（引擎可达，无生产入口）**

```
arc_check -> outline -> writing -> deslop_check -> self_review -> summary -> post_process
```

比 STREAMING 再少一个 `continuity_validation`（`self_review` 命中 `mode==FAST` 直接进 `summary`）。

> **一个实现细节**：FULL 模式下 `outline` 完成命中 fan-out 分支后，`GraphRunner` 会直接 `continue` 进入扇入目标 `world_validate`（`GraphRunner.java:131-139`），因此普通边 `edge("outline","clue_planning", FULL)` 在 FULL 模式实际被扇出分支遮蔽，不会单独走到 `clue_planning`。这条边保留是为了语义完整性与未来调整。

## 5. 两个质量门与三处回环

这条链路的核心是"写了就查、查不过就改"，回环有三处，且都被图级重试预算封顶：

| 回环 | 触发条件 | 回到的节点 | 计数依据 |
| --- | --- | --- | --- |
| 反 AI 味门禁 | `deslopDecision == REWRITE` | `writing` | 图级 `writing` 预算（≤3） |
| 自审驳回 | `severity == HIGH` 且 `writeRetryCount < 2` | `writing` | `writeRetryCount`（self_review 专属）+ 图级 `writing` 预算 |
| 审校驳回 | `auditDecision == REWRITE` / `REPLAN` | `writing` / `outline` | 图级 `writing` / `outline` 预算 |

两点必须分清，否则容易把重试上限算错：

1. **系统里有四套彼此独立的计数器**，不要混为一谈：

   | 计数器 | 作用域 | 上限 | 用途 |
   | --- | --- | --- | --- |
   | `nodeRetryCounts["writing"]` | 图级 | 3 | 任何一次"进入 writing"都计数（成功失败都算） |
   | `writeRetryCount` | 自审专属 | 2 | 只统计自审判重写（`SelfReviewNode.java:94` 自增） |
   | `deslopRewriteCount` | 反 AI 味门禁专属 | 见 `DeslopCheckNode` | 只统计 deslop 请求的重写（`DeslopCheckNode.java:112`） |
   | `rewriteCount` / `planRetryCount` | 审校路由专属 | 2 / 3 | 只统计审校 REWRITE / REPLAN（`AuditRouterNode.java:152,166`） |

   同一条 `self_review → writing` 回环会同时受第 1、2 套计数约束。

2. **兜底不能绕过一致性门**。`writing` 与 `audit_router` 的兜底都指向 `fact_lock_violation` 而不是 `summary`（`MultiAgentNovelService.java:73-79`）——预算耗尽时若直接跳 `summary`，会漏掉唯一的事实锁一致性校验，让本章被静默放行。`outline` 的兜底才是 `summary`。

**`audit_router` 有四种裁决，不是三种**。除 PASS / REWRITE / REPLAN 外还有 `MANUAL_REVIEW`：当审校自己的重写或重规划预算耗尽时（`MAX_REWRITES = 2`、`MAX_PLAN_RETRIES = 3`，`AuditRouterNode.java:23-24`），`manualReview` 只把 `auditDecision` 置为 `MANUAL_REVIEW`（`AuditRouterNode.java:265-270`），不产出 `finalResult`。

这个裁决不匹配任何条件边，于是走 `GraphRunner` 的兜底分支（`GraphRunner.java:246-250`），落到 `audit_router` 的兜底节点 `fact_lock_violation`——**仍然经过事实锁校验**，再经 `summary → post_process` 收尾。所以 MANUAL_REVIEW 的语义是"审校不再自动重试，交由一致性门兜底并放行"，而不是"章节被丢弃"。与之相对，图级 `writing` 预算耗尽时产生的 `budgetError` 会进 `state.getErrors()`，调用方能看到这一章是被强制放行的；MANUAL_REVIEW 这条路径不产生同类错误记录。

`audit_router` 的 7 维加权评分如何得到这四种裁决，见 07 篇。

## 6. 检查点与断点续跑

- 检查点声明在 `MultiAgentNovelService.java:69-71`：`outline`、`writing`、`audit_router`。
- **断点恢复只在 FULL 模式触发**（`GraphRunner.java:53` 的 `mode == Mode.FULL && checkpointService != null`）。STREAMING / FAST 不做断点恢复。
- 恢复时从最近的检查点节点重新进入，重算下一跳（`GraphRunner.java:56-69`）。
- 检查点带 1 小时 TTL（`StateCheckpointService.java:19`），整章跑完后统一清理（`GraphRunner.java:157-160`）。

## 7. 取消与断线

**真正让图停下来的机制**是"客户端断流 → 内存取消标志"这条链：

1. 前端点"取消生成"，先 `abort()` 掉 SSE fetch（`frontend/src/views/NovelDetail.vue:932`）；
2. 连接断开后 Spring 的 `SseEmitter` 触发 `onError`，控制器把内存里的 `cancelFlag` 置 `true`（`StreamingChapterController.java:114-117`）；
3. `GraphRunner` 在每个节点边界检查 `state.getCancelFlag()`，命中即 `break`（`GraphRunner.java:81-84`）。

前端还有一条 10 分钟超时兜底，超时也 `abort()`（`NovelDetail.vue:761`）。

**如实记录的一处易误解点**：`/chapter/cancel` 接口确实会往 Redis 写 `xpb:novel:cancel:{novelId}`（10 分钟 TTL，`StreamingChapterController.java:223`），但**这条单章流式链路里它只写不读**——流内既不在开始之外的地方读它，也不靠它停图。真正读取"取消键"的是向导批量生成流程，且用的是另一命名空间 `xpb:novel:wizard:batch:cancel:{taskId}`（`WizardServiceImpl.java:420`）。所以单章流式生成能否停下来，取决于上面的内存标志，而不是这个 Redis 键。

**防重复提交**：同一"小说 + 章节"同时只允许一个流式生成，用 `activeStreams.putIfAbsent` 拦截，重复请求直接回一个 error 事件（`StreamingChapterController.java:88-98`）。

## 8. 落库与产物

正文的自动落库发生在图内 `post_process` 节点，而不是控制器：

- **自动落库**（FULL 与 STREAMING 正常走完都会经过）：`post_process` 调 `chapterSaveService.saveGenerationResultAsync(...)` 把正文异步写入 MySQL `novel_chapter`（最多重试 3 次），随后异步更新长期记忆三件套 `FactLock` / `EmotionLedger` / `CompletedBeats`（`PostProcessNode.java:66-118`）。摘要由上游 `summary` 节点产出（`SummaryNode.java:59-68` 写 `finalResult.finalContent`/`wordCount`）。
- **手动落库**（取消或校验失败时）：正文没跑到 `post_process`，前端在本地缓冲 `streamingContent`，用户确认后调 `/chapter/stream-save`，走**同步**的 `saveGenerationResult` 补存（`StreamingChapterController.java:230-264`）。
- **避免双写**：控制器的正常分支只发 `complete` SSE 事件、不再次保存（`StreamingChapterController.java:175-186`）——保存统一交给图内 `post_process`，控制器不重复落库。

字数口径：`wordCount` 用"去掉全部空白后的字符数"（`content.replaceAll("\\s+", "").length()`，`WritingNode.java:132` / `StreamingChapterController.java:255`）。
