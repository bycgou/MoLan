# 墨韵 AI 小说创作系统 — 外部记忆系统与反 AI 味完整方案

---



## 第一部分：外部记忆系统

### 一、设计目标

```
核心问题：AI 写第300章时，仍然记得第3章埋的伏笔、角色的性格底线、
         以及上一章结尾的悬念。

设计原则：
1. 结构化数据为主，向量检索为辅
2. 精确查询优先，语义检索兜底
3. 每章更新，实时反映故事最新状态
4. 分层存储，各层职责清晰不重叠
5. 兼容现有 MySQL + MongoDB + Redis 架构
```

### 三、各层详细设计

#### 第一层：故事状态（StoryState）— 核心枢纽

**定位**：相当于作者写到当前章节时桌上的"剧情进度表"，是整个记忆系统的核心枢纽。

**存储位置**：MongoDB `story_state` 集合（新增）

**更新频率**：每生成一章后自动更新

**注入方式**：每次生成章节时全量注入 Prompt（约 500-800 字）

```json
{

  "lastChapter": 86,

    "physicalCondition": "右手经脉受损",
```

**与现有系统的关系**：
- 不替代 `CharacterState`（角色长期档案），两者互补
- 不替代 `NovelMemory`（长周期背景压缩），两者共存
- 是 Prompt 组装的**第一优先级数据源**

---

#### 第二层：伏笔账本（Foreshadow Ledger）

**定位**：所有伏笔的精确追踪器，确保不遗忘、不错过回收时机。

**存储位置**：MySQL `clue_book` 表（已有）

**更新频率**：每章生成后检查伏笔状态变化

**注入方式**：SQL 精确查询，按条件注入

```
查询规则：

1. 到期预警：deadline <= 当前章号 + 5 的未回收伏笔
   → 注入："以下伏笔即将到期，本章必须推进或回收"

2. 近期埋设：bury_chapter >= 当前章号 - 10 的未回收伏笔
   → 注入："以下伏笔刚埋下，需要适当推进"

3. 全局概览：所有未回收伏笔，按 deadline 排序，取前10条
   → 注入："当前未回收伏笔概览"
```

**不依赖 RAG，不依赖向量检索，纯结构化查询。**

---

#### 第三层：角色档案（Character Profile）

**定位**：角色的长期记忆，记录角色从出场到现在的完整档案。

**存储位置**：MySQL `novel_character`（基础设定）+ MongoDB `character_state`（动态状态）

**更新频率**：角色状态变化时更新

**注入方式**：按本章出场角色精确查询，只注入涉及的角色

```
注入内容：
- 基础设定（性格、背景、首次出场）← MySQL
- 当前状态（情绪、位置、成长轨迹）← MongoDB character_state
- 禁止行为（forbiddenBehaviors，防止OOC）← MongoDB character_state
- 与其他出场角色的关系值 ← MongoDB character_state.relationshipMap
```

---

#### 第四层：滑动窗口（Sliding Window）

**定位**：保证章节之间的微观衔接，让 AI 知道"刚刚发生了什么"。

**存储位置**：MySQL `novel_chapter`（章纲+正文）+ MongoDB `chapter_summary`（摘要）

**更新频率**：每章生成后自动追加

**注入方式**：按章节号顺序查询（不按向量相似度）

```
注入内容：

1. 最近3章完整章纲 ← MySQL novel_chapter
2. 最近5章正文摘要 ← MongoDB chapter_summary
3. 上一章结尾原文（最后500字）← MySQL novel_chapter.content
```

**这是替代现有"近8章大纲"的方案，信息密度高得多。**

---

#### 第五层：知识图谱（Knowledge Graph）

**定位**：实体关系的结构化查询引擎。

**存储位置**：MongoDB `novel_graph`（已有）

**更新频率**：关系变化时更新

**注入方式**：按本章涉及的实体精确查询

```
查询方式：
1. 角色关系子图：本章涉及角色之间的所有关系边
2. 地点关联查询：本章场景地点相关的历史事件
3. 物品关联查询：本章涉及物品的历史流转
```

---

#### 第六层：RAG 向量检索（Vector Recall）

**定位**：最后的兜底手段，用于回忆早期章节的具体细节。

**存储位置**：MongoDB `chapter_summary`（embedding）+ Redis Stack 向量索引

**更新频率**：每章生成后，新摘要的 embedding 写入

**触发方式**：Agent 主动调用（通过 LangChain4j `@Tool`），不是每次都跑

```
Agent 在写作过程中，遇到以下情况主动调用：
- 需要回忆某个早期事件的具体细节
- 需要回收一个很久以前埋的伏笔
- 角色重逢场景，需要回忆上次见面的具体情况
```

**关键变化**：RAG 从"每次生成都跑"变为"Agent 按需调用"，减少无效上下文注入。

## 第二部分：反 AI 味系统

### 一、AI 味的六个具体表现

```
1. 情节节奏模板化
   冲突出现 → 短暂受挫 → 灵光一闪 → 逆转胜利 → 感慨升级
   读者读3次就知道后面会发生什么

2. 角色反应公式化
   愤怒 = 双拳紧握 + 眼中寒光 + "你找死"
   震惊 = 瞳孔微缩 + 满脸不可置信
   每个角色的同一情绪都是同一个模板

3. 过渡句万能胶
   "时间飞逝，转眼三天过去了"
   "与此同时，另一边……"
   "就在XXX即将XXX的时候……"

4. 升级/收获描写流水账
   盘膝而坐 → 运转功法 → 灵力奔涌 → 气息爆发 → 
   睁开双眼 → 嘴角笑意 → 凝真高阶！

5. 对话结构单一
   A说 → B反应描写 → B回应 → A内心 → A再说
   永远是这个循环，缺少沉默、打断、答非所问

6. 缺乏"无用"细节
   AI："林辰走进大殿，看到长老们已经到齐"
   人类："林辰走进大殿时踩到了门槛，差点绊倒。
          长老们已经到齐，三长老在抠指甲"
```

### 二、四道防线

```
第一道：章纲层面（OutlineAgent）
  ↓
第二道：正文层面（WritingAgent）
  ↓
第三道：检查层面（StyleAuditAgent）
  ↓
第四道：修正层面（局部重写）
```

#### 第一道防线：章纲层面

在 OutlineAgent 生成章纲时注入**叙事结构多样性规则**：

```
1. 禁止连续3章使用相同叙事视角
   （主角视角 → 配角视角 → 反派视角 → 旁观者视角 交替）

2. 每卷至少2章使用非线性叙事
   （倒叙、插叙、多线并行）

3. 战斗结局不能全是"主角险胜"
   （平局 / 惨胜 / 被迫撤退 / 赢了但失去重要东西 / 敌人主动退走）

4. 每5章至少1章的核心冲突不是外部战斗
   （内心挣扎 / 人际矛盾 / 道德困境 / 信息不对称的误解）

5. 偶尔打破"每章都有钩子"的规则
   （有些章节平淡收尾，制造节奏变化，让有钩子的章节更有力）
```

**这是最根本的一道防线——从结构层面保证故事不可预测。**

#### 第二道防线：正文层面

在 WritingAgent 的系统指令中注入**反模板规则**：

```
【反AI味规则 — 写作铁律】

1. 禁止使用以下过渡句：
   "时间飞逝，转眼X天过去了"
   "与此同时，另一边"
   "且不说XXX，单说XXX"
   "就在XXX即将XXX的时候"
   → 替代方案：直接切场景，不需要过渡

2. 角色反应多样性：
   - 愤怒不一定握拳瞪眼（可以沉默、可以笑、可以转移话题）
   - 震惊不一定瞳孔微缩（可以手抖、可以反复确认、可以失语）
   - 同一情绪在不同角色身上必须有不同的外在表现

3. 对话节奏：
   - 每5轮对话至少1次：沉默、打断、答非所问、被第三方打断
   - 对话中穿插动作描写，但动作不能全是"看着对方""点了点头"

4. 场景细节：
   - 每个新场景至少1个与主线无关的感官细节
   （声音、气味、触感、光线、无关人物的小动作）

5. 禁止每章结尾都是"主角嘴角勾起一抹笑意"
```

**同时注入文风卡片的全部规则**（节奏、对话、描写、禁用词、偏好词、原文样本）。

#### 第三道防线：检查层面

**新增 StyleAuditAgent**，正文生成后自动运行：

```
检测维度：

1. 禁用词检测
   → 扫描正文是否包含 forbiddenRules 中的词汇

2. 句式重复检测
   → 统计句式多样性指数，与文风卡片 statsJson 对比
   → 如果多样性指数低于原文的60%，标记为AI味过重

3. 对话结构检测
   → 统计对话模式分布
   → 如果连续5轮对话都是"A说→B回应"，标记

4. 过渡句检测
   → 扫描是否存在禁用的万能过渡句

5. 角色情绪表达重复检测
   → 同一情绪的外在表现是否与前文重复

6. 场景细节检测
   → 检查新场景是否有至少1个无关主线的感官细节

7. 伏笔一致性检测
   → 本章涉及的伏笔是否与 clue_book 一致

8. 实力等级一致性检测
   → 本章提到的实力等级是否与 story_state 一致

输出：
{
  "overallScore": 78,
  "issues": [
    {"type": "forbidden_word", "location": "第3段", "word": "不禁"},
    {"type": "template_reaction", "location": "第7段", "detail": "愤怒描写与第52章重复"},
    {"type": "missing_detail", "location": "第1段", "detail": "新场景缺乏感官细节"}
  ],
  "autoFixable": true
}
```

#### 第四道防线：修正层面

```
如果 StyleAuditAgent 检测不通过：

1. 自动修复（autoFixable = true）：
   → 禁用词替换
   → 过渡句替换
   → 缺失的感官细节补充
   → 用更多样本片段作为参考，触发局部重写

2. 标记给用户（autoFixable = false）：
   → 严重的情节模板化
   → 角色OOC
   → 结构性问题

3. 最多重写2次，超过则标记给用户手动处理
```

### 三、文风卡片改进

#### 改进一：增加反模式维度

在分析阶段增加程序化检测：

```
1. 句式多样性指数
   → 统计原文句式变化频率
   → 生成后对比，低于基准值则标记

2. 过渡方式偏好
   → 扫描原文场景过渡方式
   → 是直接切场景还是用过渡句

3. 章尾模式分布
   → 扫描每章最后200字
   → 统计章尾类型分布

4. 情绪表达多样性
   → 扫描每种情绪的外在表现种类数
   → 作为生成后对比的基准
```

#### 改进二：增加样本类型

现有5类（悬疑/对话/战斗/心理/描写），增加6类：

| 新增样本类型     | 作用                                    |
| ---------------- | --------------------------------------- |
| `transition`     | 场景过渡片段，AI最弱的环节              |
| `silence`        | 沉默/无对话的场景，AI总充斥对话         |
| `detail`         | 无关主线的细节描写，让场景活起来        |
| `inner_conflict` | 内心挣扎/道德困境，AI容易写得肤浅       |
| `humor`          | 幽默/轻松片段，AI写的幽默通常很尴尬     |
| `anti_climax`    | 反高潮/平淡收尾，打破"每章结尾都是悬念" |

#### 改进三：检查从事后改为事中+事后

```
事中检查（章纲生成后）：
  → 检查叙事结构是否符合风格要求
  → 此时修改成本低

事后检查（正文生成后）：
  → 检查用词、句式、对话比例等表层风格
  → 对比 statsJson 量化指标
  → 标记偏离度过大的段落
  → 自动触发局部重写
```

## 第三部分：逻辑功能总结

### 一、章节生成完整流程

```
阶段一：规划生成
  用户输入（主线/文风/题材/世界观/核心设定）
    → PlanningAgent 生成卷纲 + 核心人物 + 分卷规划
    → 用户确认/修改
    → 确认后写入 novel_arc + novel_character

阶段二：章纲生成（逐卷）
  对每一卷：
    → OutlineAgent 生成本卷所有章纲
       输入：总纲 + 本卷任务 + 故事状态 + 前卷摘要 + 伏笔规划 + 叙事多样性规则
    → 质量检测（重复/伏笔/节奏/钩子/逻辑/注水）
    → 用户审阅/修改/确认
    → 更新故事状态

阶段三：正文生成（逐章）
  对每一章：
    → Prompt 组装引擎组装完整上下文（六层记忆 + 文风卡片 + 章纲）
    → WritingAgent 生成正文（可按需调用 RAG @Tool）
    → StyleAuditAgent 检查一致性 + AI味
    → 不通过则自动修正或标记用户
    → 后处理流水线更新所有状态
```

### 二、后处理流水线（每章生成后自动执行）

```
Step 1: SummaryAgent 生成本章摘要
        → 写入 MongoDB chapter_summary
        → 生成 embedding 写入 Redis 向量索引

Step 2: 更新故事状态
        → 读取当前 story_state
        → SummaryAgent 提取本章状态变化
        → 写入新版本 story_state (version+1)

Step 3: 更新角色状态
        → 本章涉及角色的 character_state 更新
        → 情绪、位置、成长节点等

Step 4: 更新知识图谱
        → 新角色/新关系/关系变化 → 更新 novel_graph

Step 5: 检查伏笔
        → 本章是否回收了某个伏笔 → 更新 clue_book status
        → 本章是否埋设了新伏笔 → 写入 clue_book

Step 6: AuditAgent 审计
        → 一致性检查（实力/位置/时间线）
        → AI味检查（禁用词/句式/模板）
        → 结果写入 audit_log

Step 7: 更新世界时钟
        → 推进 story_state.timeline
```

### 四、一句话总结

**记忆系统的本质是让 AI "知道自己知道什么"**——通过六层结构化记忆，让 AI 在写每一章时都能精确获取所需信息，而不是靠模糊的语义检索碰运气。

**反 AI 味的本质是让 AI "不那么像 AI"**——通过四道防线（结构多样性 → 写作规则约束 → 生成后检测 → 自动修正），从章纲到正文逐层降低可预测性和模板化。

**文风卡片是两者的桥梁**——它既是记忆系统注入 Prompt 的风格载体，也是反 AI 味系统检测和修正的对比基准。三者协同，才能让 AI 生成的小说从"能看"变成"想看"。
