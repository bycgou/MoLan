# 02 · 图编排引擎

> 自研的有向图执行引擎，是本系统「以编排本身为研究对象」的落点。LangChain4j 负责单次 LLM 调用，本引擎负责**节点拓扑、状态传递、条件路由、并发扇出扇入、错误隔离与重试预算**。

---

## 1. 设计目标与边界

长篇创作的难点不是「让模型写一段好文字」，而是「让几十个环节按正确的顺序、在正确的上下文里、以可控的代价完成」。系统因此把创作流程显式建模成一张**有向图**：

| 目标 | 引擎侧的机制 |
| --- | --- |
| 流程可声明、可审阅 | `GraphDefinition` 是纯数据（不可变 record + Builder），拓扑不写在代码逻辑里 |
| 状态在节点间传递且可持久化 | `NovelAgentState` 不可变对象，经 Jackson 序列化进 Redis 检查点 |
| 失败可隔离而非整体崩溃 | 节点级 `ErrorStrategy`（SKIP / RETRY / FAIL）+ 图级重试预算 |
| 循环不会无限 | 迭代上限 20 步 + 节点级预算（进入次数）双重约束 |
| 分支可并行 | fan-out / fan-in，配可插拔的 `MergeStrategy` |

**明确不做什么**：本引擎不是工作流编排平台（不提供通用 DSL、不做定时调度、不做分布式补偿事务）；它只服务于"生成一章小说"这一条链路，因此被刻意做小。

## 2. 组成结构

```
ai/graph/
├── GraphDefinition.java      图定义（纯数据）：边、条件边、扇出扇入、检查点、重试策略
├── GraphRunner.java          图执行器：驱动节点、路由、并发扇出、迭代与预算控制
├── NodeExecutor.java         节点执行包装：AuthorAgent 钩子、重试、检查点落盘
├── NovelGraphNode.java       节点接口（apply + 4 个扩展点）
├── NovelAgentState.java      全局状态载体（不可变，@Builder(toBuilder=true)）
├── StateHelper.java          状态的纯函数式操作（追加 trace / error / 计次 / 合并意见）
├── Mode.java                 运行模式：FAST / STREAMING / FULL
├── ErrorStrategy.java        节点错误策略：SKIP / RETRY / FAIL
├── StructuredError.java      结构化错误（节点名、策略、消息、是否可恢复）
├── NodeExecutionRecord.java  单节点执行记录（名称、耗时、指令、元数据）
├── MergeStrategy.java        扇出合并策略
├── StateCheckpointService.java  检查点读写（Redis）
├── StateSnapshot.java        检查点快照
└── AuthorAgent / AuthorDirective / AuthorAgentConfig / AuthorAgentImpl
                              作者审校钩子（详见 06 篇）
```

代码位置：`backend/src/main/java/com/novel/system/ai/graph/`。

## 3. 图定义：声明式拓扑

`GraphDefinition` 用 Builder 声明四类拓扑元素，全部为不可变 `record`（`backend/src/main/java/com/novel/system/ai/graph/GraphDefinition.java:28-31`）：

| 元素 | 语义 | Builder 方法 |
| --- | --- | --- |
| `Edge` | 无条件边，可限定生效模式 | `edge(from, to[, mode])` |
| `ConditionalEdge` | 条件边，谓词命中即跳转 | `conditionalEdge(from, to, predicate[, mode])` |
| `FanOutGroup` | 扇出：一个节点并发触发多个分支 | `fanOut(source, targets, mode[, strategy])` |
| `FanInGroup` | 扇入：多分支汇聚到一个节点 | `fanIn(sources, target, mode)` |

此外还有 `checkpoint(node)` 声明检查点节点、`retryPolicy(node, maxRetries, fallback)` 声明节点级预算与兜底节点（`GraphDefinition.java:170-179`）。

### 3.1 路由规则：条件边优先，先命中先赢

`getNextNode` 先遍历条件边、再遍历普通边，**第一个命中的条件边决定下一跳**；都不命中则返回 `END`（`GraphDefinition.java:33-49`）。这个顺序有实际后果：同一节点上有多条条件边时，**声明顺序即优先级**，生产图里必须把特判写在默认分支之前。

### 3.2 模式限定边

边的 `modes` 集合为空表示所有模式生效；非空时仅在指定模式生效（`GraphDefinition.java:117-119`）。这是同一张图支持 FAST / STREAMING / FULL 三档的机制——**不是三张图，而是一张图按模式裁剪**。`isFanOut(node, mode)` 专门做了模式校验，避免在不支持扇出的模式（如 FAST）里误入扇出分支（`GraphDefinition.java:59-62`）。

## 4. 节点接口与扩展点

```java
public interface NovelGraphNode {
    NovelAgentState apply(NovelAgentState state) throws Exception;
    String nodeName();
    default boolean shouldSkip(NovelAgentState state)      { return false; }
    default ErrorStrategy errorStrategy()                    { return ErrorStrategy.SKIP; }
    default int maxRetries()                                 { return 2; }
    default NovelAgentState resetState(NovelAgentState s, String source) { return s; }
}
```

（`NovelGraphNode.java`）

| 扩展点 | 作用 |
| --- | --- |
| `apply` | 节点主体，返回新的状态对象 |
| `shouldSkip` | 命中则跳过该节点并记一条 skipped 轨迹 |
| `errorStrategy` | 决定该节点失败后的处理方式 |
| `maxRetries` | 仅当 `errorStrategy=RETRY` 时生效 |
| `resetState` | **流程重新路由回该节点时**声明如何清理状态（如清掉上一轮草稿），避免旧数据污染新一轮 |

`resetState` 是"重写"类边（`deslop_check → writing`、`self_review → writing`）能正确工作的前提：重新进入写作节点时必须先清空上一轮产出。

## 5. 状态载体

`NovelAgentState` 是**不可变**对象，所有修改通过 `toBuilder()` 生成新实例（`@Builder(toBuilder=true)`）。字段可分四组：

| 组 | 代表字段 |
| --- | --- |
| 标识与输入 | `novelId`、`chapterNum`、`userIntent`、`styleCardId`、`llmConfigId`、`rhythmTag` |
| 流程产物 | `outlineContext`、`writingContext`、`chapterPlan`、`preWriteValidation`、`selectedIdea`、`draftContent`、`auditResult`、`finalResult` |
| 控制与计次 | `iterationCount`、`planRetryCount`、`writeRetryCount`、`rewriteCount`、`auditDecision`、`currentPhase`、`nodeRetryCounts`、`deslopRewriteCount`、`deslopDecision` |
| 观测与异常 | `executionTrace`、`errors`、`llmCalls`、`authorDirective`、`pendingRevisionNotes`、`deslopFindings`、`cancelFlag`、`sseEmitter` |

不可变带来两个直接好处：一是状态可以安全地在扇出分支间共享（各分支基于同一 base 派生副本）；二是可以整体序列化进 Redis 而不用担心并发修改。

`StateHelper` 提供全部状态操作，均为纯函数（`StateHelper.java`）：`appendTrace`、`appendError`、`appendLlmCall`、`incrementNodeRetry`、`getNodeRetryCount`、`mergeRevisionNotes`（上限 `MAX_REVISION_NOTES = 12`）、`truncate` 等。

## 6. 执行流程

### 6.1 驱动主循环

`GraphRunner.executeFrom` 是核心循环（`GraphRunner.java:75-163`），每一步依次做：

1. **检查取消标志** —— `state.getCancelFlag()` 为真则中止（客户端断开场景）；
2. **检查迭代上限** —— `MAX_ITERATIONS = 20`，超出则记一条 `FAIL` 错误并结束；
3. **取节点** —— 未注册则记错并结束；
4. **执行节点** —— 交给 `NodeExecutor`（无 `NodeExecutor` 时退化为直接 `apply`）；
5. **追加执行轨迹** —— `NodeExecutionRecord.success(...)`；
6. **处理扇出** —— 若当前节点是扇出源，转 `executeFanOut`，再跳到扇入目标；
7. **路由下一跳** —— `getNextNode`（含重试预算保护）；
8. **重置下一跳的状态** —— 调用下一节点的 `resetState(state, currentNode)`。

图执行结束后清空该章的检查点（`GraphRunner.java:157-160`）。

### 6.2 并发扇出

`executeFanOut` 用 `CompletableFuture.supplyAsync` 在固定线程池上并行执行各分支（`GraphRunner.java:168-211`）。两点值得注意：

- 单个分支超时上限 **60 秒**（`futures.get(i).get(60, TimeUnit.SECONDS)`），超时或异常时该分支降级为一条可恢复错误，不影响其他分支；
- 合并由 `MergeStrategy` 决定。`defaultStrategy()` 累积所有分支的 `executionTrace` / `errors` / `llmCalls`；`chapterPlanMerge()` 在此基础上合并 `chapterPlan` 的 `clueActions` 与 `characterActions`——伏笔规划分支与人物动线规划分支各写一半章纲，靠这个策略拼回完整章纲（`MergeStrategy.java`）。

### 6.3 检查点与断点续跑

`StateCheckpointService` 把状态快照写入 Redis（`StateCheckpointService.java:35-49`）：

- 键由 `RedisKeyProvider.checkpoint()` 提供前缀，形如 `<prefix>novel:checkpoint:<novelId>:<chapterNum>:<nodeName>`；
- **TTL 为 1 小时**（`StateCheckpointService.java:19`）；
- 恢复时按管线顺序 `["outline", "writing", "audit_router"]` 找最近的检查点（`StateCheckpointService.java:20-22`）。

断点恢复只在 `Mode.FULL` 下触发（`GraphRunner.java:53`）：`execute` 先查检查点，命中则反序列化状态、从检查点所在节点的**下一跳**继续执行。

> **边界**：流式（STREAMING）模式走的是 `Mode.STREAMING`，**不会**触发检查点恢复分支。也就是说"浏览器关掉后接着上次继续流式生成"目前不成立；实际做法是前端保留已产出内容，由用户触发手动保存。

## 7. 错误处理与重试预算

### 7.1 两层错误处理

| 层 | 机制 | 语义 |
| --- | --- | --- |
| 节点内重试 | `NodeExecutor.executeWithRetry` | 同一节点内按 `maxRetries` 重试，成功或失败都只算**一次进入** |
| 图级预算 | `GraphRunner.resolveWithRetryProtection` | 统计节点被**进入的次数**，超预算则改道兜底节点 |

`ErrorStrategy` 三态（`ErrorStrategy.java`）：`SKIP` 跳过并用默认值继续、`RETRY` 在节点内重试、`FAIL` 终止流程。图定义里按节点名指定默认策略（`GraphDefinition.java:101-107`）：`outline` / `writing` 为 `RETRY`，`audit_router` 为 `FAIL`，其余为 `SKIP`。

### 7.2 「进入即计数」的预算语义

`nodeRetryCounts` 记录的是**该节点被进入的次数**，成功和失败**都计一次**。计数在 `apply` 之前完成，并把带计数的状态传给节点（`NodeExecutor.java:74-79`），这样节点内部（如路由保护）看到的状态已经包含本次进入。

这个语义很关键：如果只在成功时计数，一个持续抛异常的节点将永远不消耗图级预算，会被反复重入直到撞上 20 步迭代上限——问题被掩盖成"跑了很久才停"，而不是"这个节点坏了"。

### 7.3 降级必须留痕

预算耗尽时，`resolveWithRetryProtection` 返回的不只是兜底节点名，还带一条 `StructuredError`，内容形如：

```
writing 重写预算耗尽(3/3)，已强制放行到 fact_lock_violation
```

该错误会被追加进 `state.getErrors()`（`GraphRunner.java:141-145`），最终出现在 `AgentExecutionResult.errors` 里。**没有这条错误，调用方无从知道这一章是被强制放行的**，这正是静默降级最危险的地方。

为避免 `GraphRunner` 作为单例时的并发串扰，预算错误通过返回值传递（`NextHop` record，`GraphRunner.java:283`）而非实例字段。

### 7.4 兜底路径不能绕过一致性门

生产图里 `writing` 与 `audit_router` 的兜底节点都是 `fact_lock_violation` 而不是 `summary`（`MultiAgentNovelService.java:72-79`）。原因：跳到 `summary` 会绕过唯一的事实锁校验，本章被静默放行；改走 `fact_lock_violation` 则至少把一致性校验做完再收尾。`outline` 的兜底是 `summary`，因为它本来就没有正文。

## 8. 执行结果与可观测性

一次执行产出 `AgentExecutionResult`（`AgentExecutionResult.java`）：

| 字段 | 内容 |
| --- | --- |
| `content` / `wordCount` | 最终正文 |
| `qualityScore` | 质量评分 |
| `executionTrace` | 节点序列与状态 |
| `errors` | 结构化错误（已压平为 `"节点名: 消息"`） |
| `elapsedMs` | 总耗时 |

节点级细节另有三处落点：`NodeExecutionRecord`（含单节点耗时与当时的作者指令）、`LlmCallRecord`（每次 LLM 调用的模型、耗时、token 数）、`AgentMetrics`（指标埋点）。

> **边界**：系统**没有**独立的"生成轨迹时间线"页面。执行轨迹随章节接口返回，章节详情页以剧情摘要字段（`plotFingerprint`）呈现节点序列；节点级耗时以服务端日志为准。

## 9. 为什么自研而不用现成编排库

| 维度 | 自研 | 现成工作流库 |
| --- | --- | --- |
| 依赖体积 | 零额外依赖 | 引入框架及其配置体系 |
| 状态模型 | 与业务对象同一套 `NovelAgentState`，序列化即检查点 | 需在框架状态与业务状态之间做映射 |
| 错误语义 | 业务级 `ErrorStrategy` + 可追溯降级 | 框架级重试/补偿，与"这一章是否被放行"的业务语义不匹配 |
| 论文价值 | 拓扑、状态传递、节点调度本身即研究对象 | 成了框架的使用者 |

自研的代价是**所有边界条件都得自己扛**（迭代上限、预算语义、扇出超时、降级留痕），这些恰好构成本课题在"编排基础设施"方向上的可验证内容。
